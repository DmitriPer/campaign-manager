# תוכנית משימות — Campaign Manager

סטטוס: האפיון והתכנון הטכני מוכנים לעבודה. כל משימות המימוש בהמשך ממתינות. המקורות הם [אפיון ותנאי קבלה](PRODUCT_SPEC.md#תנאי-קבלה), [ארכיטקטורה](ARCHITECTURE.md#first-pilot-architecture) ו־[יומן החלטות](DECISIONS.md#first-pilot-decisions).

## יעד הפיילוט

מאסטר ושחקן ניגשים משני מכשירים, משלימים הצטרפות עם עותק דמות עצמאי, מעדכנים HP ואפקטים בסשן ומקבלים את אותו מצב אחרי חיבור מחדש ובסיום. הצלחה כוללת גם בדיקה של חשבון שלישי ללא הרשאה.

## לפני T01

- ✅ ענף `dev` נוצר מ־`main`, וכלל ה־PR חל על `main` ועל `dev` (נבדק ב־2026-11-19). ענפי עבודה יוצאים מ־`dev`.
- צור חשבון Supabase ופרויקט חינמי בשם `dev`. ‏Vercel ו־Google OAuth נדרשים רק בשלב האירוח (T09).
- Docker במחשב אינו חובה (A19). מומלץ להתקין אותו כשמגיעים לבדיקות הרשאות, כדי להריץ Supabase מקומי שאפשר לאפס. ב־CI הוא זמין ממילא בשרתים של GitHub. בלינוקס נמצא Node.js 24.15.0 עם npm 11.12.1.

## אופן עבודה וסיום משימה

- התחל ב־T01. ‏T03 ו־T04a עצמאיות לאחר T02a, ו־T04b אחרי T04a. ‏T02b יכולה לרוץ במקביל להן. יש לרשום ב־[מסמך ההתקדמות](PROGRESS.md) את המשימה הפעילה ואת תוצאות האימות.
- פתח ענף עבודה והגש PR לפי מדיניות המאגר. משימת מימוש מסתיימת כשהתוצר, בדיקות הקבלה הרלוונטיות והתיעוד נמצאים באותו שינוי. תעד מה הורץ בפועל.
- בדיקות יחידה מכסות חישובי HP ומעברי מצב. בדיקות pgTAP ובדיקות עם לקוחות מקבילים מול Supabase מכסות הרשאות, טרנזקציות ומרוצים. בדיקות דפדפן מכסות את הזרימה בעברית ואת התצוגה בשני לקוחות.
- תעד החלטות חדשות עם מזהה ביומן. התאם את האפיון כשמשתנה התנהגות, ואת הארכיטקטורה כשמשתנות תשתית או בעלות על נתונים.

## ענפים וגרסאות

| ענף | תפקיד | איך נכנסים שינויים |
| --- | --- | --- |
| `main` | קו הייצור ומקור הגרסאות הרשמיות | PR לקידום גרסה שנבדקה מ־`dev`, או PR לתיקון חירום. פריסה לייצור משתמשת בגרסה המתויגת. |
| `dev` | ענף ברירת המחדל. שילוב הגרסה הקרובה ומקור ל־staging כשיקום | PR מענף עבודה. מריצים את בדיקות השילוב של הגרסה הקרובה על staging עם נתונים נפרדים. |
| `feature/<task>-<name>`, `fix/<name>`, `docs/<name>`, `chore/<name>` | שינוי ממוקד וזמני | מסתעפים מ־`dev` ומגישים PR חזרה אליו. אפשר לבצע squash ל־PR של ענף עבודה. |
| `hotfix/<name>` | תיקון דחוף לגרסה בייצור | מסתעפים מ־`main`, מגישים PR ל־`main`, מתייגים גרסת תיקון ומחזירים את התיקון ל־`dev` דרך PR. |

- הגן על `main` ו־`dev` מפוש ישיר, force push ומחיקה. אחרי שריצות CI קיימות ומדווחות ל־GitHub, הגדר אותן כבדיקות חובה. עבודה של מפתח יחיד יכולה להישאר עם 0 אישורים נדרשים לפי ההגדרה שסוכמה.
- קידום רגיל הוא PR מ־`dev` ל־`main`. השתמש ב־merge commit בקידום ובסנכרון חזרה כדי לשמר את ההיסטוריה בין הענפים הקבועים. בצוות קטן מקבעים את תוכן `dev` בזמן בדיקת השחרור. מוסיפים ענף `release/*` רק אם נדרש להמשיך למזג פיצ׳רים בזמן ייצוב גרסה.
- גרסת האפליקציה נפרדת מגרסת Angular. השתמש במספור SemVer ובתג Git בלתי משתנה על ה־commit ששוחרר מ־`main`. לדוגמה, `v0.1.0` לפיילוט שמוכן לשחרור, `v0.1.1` לתיקון ו־`v0.2.0` לתוספת משמעותית. בשלב `0.x` חוזי המוצר עדיין יכולים להשתנות. צרף ל־GitHub Release סיכום שינויים והנחיות מיגרציה אם יש.
- לפני שחרור ודא ש־CI עבר על תוצאת המיזוג, בדוק את תרחישי הליבה ב־staging ותעד את גרסת ה־DB ודרך החזרה במקרה כשל. בצע smoke test גם אחרי פריסה. אם הייתה מיגרציה, חזרה לגרסת קוד קודמת דורשת לוודא שהסכמה עדיין תואמת.

## תחזוקת Angular

בדוק פעם בחודש אם יצאה גרסה יציבה חדשה וטפל בתיקוני אבטחה רלוונטיים בהקדם. עדכן את Angular וה־CLI יחד ב־PR ייעודי, עם הרצת המיגרציות של `ng update` ובדיקת תאימות Node.js, ‏TypeScript ותלויות. גרסת major מעדכנים צעד אחד בכל פעם. לפני מיזוג, הרץ התקנה נקייה, בנייה ובדיקות CI. כשזרימת הפיילוט תהיה זמינה, בדוק גם כניסה ועדכון HP משני לקוחות. [מדיניות השדרוג](ARCHITECTURE.md#angular-maintenance)

## אחרי הפיילוט

1. הרחבת חברות ועריכת נתוני בסיס, כולל הזמנות פרטיות, עזיבה ומדיניות Max HP. השלם את כללי ההשהיה והסיכומים לפני הרחבת הסשנים.
2. עולם, מיקומים, מסמכים ו־NPCs. תכנן ייבוא JSON נפרד משחזור והשתמש בנתוני הסבה מורשים.
3. קרב ידני, בחירת משתתפים, יוזמה, חוליות והיסטוריית קרב. כולם משתמשים במצב החי הקיים.
4. מפות, סמנים ותצוגת טלוויזיה מוגבלת. הגדר הרשאות והצגת מידע לפני חיבור נתוני אמת.
5. משאבים, שיפורי שימוש וחילוץ PDF לפי דוגמאות. [שאלות המשך](DECISIONS.md#open-questions)
